# NFR Design Patterns — Unit 2: iPhone Foundation

---

## Pattern 1: Repository Pattern via Protocol-Backed Services (Maintainability + Testability)

### Applies To
`AuthServiceProtocol`, `FirebaseServiceProtocol`, `HealthKitServiceProtocol`, `OfflineSessionQueueProtocol`

### Design
All infrastructure dependencies are hidden behind Swift protocols. ViewModels receive protocols, not concrete implementations. `AppContainer` (the composition root) creates the real implementations at startup. Tests use mock implementations.

```
ViewModel
  └── depends on: FirebaseServiceProtocol
                     ↑
        ┌────────────┴────────────┐
  FirestoreService          MockFirebaseService
  (production)              (tests)
```

No ViewModel imports Firebase SDK — only the service layer does. This means:
- ViewModels can be unit tested without a real Firebase connection
- The Firebase SDK can be swapped without touching any ViewModel
- Mock services in tests return predictable data instantly

### AppContainer Wiring
```swift
final class AppContainer {
    let authService: AuthServiceProtocol
    let firebaseService: FirebaseServiceProtocol
    let healthKitService: HealthKitServiceProtocol
    let offlineQueue: OfflineSessionQueueProtocol

    init() {
        self.authService = FirebaseAuthService()
        self.firebaseService = FirestoreService()
        self.healthKitService = HealthKitService()
        self.offlineQueue = CoreDataOfflineQueue()
    }
}
```

## Pattern 2: Cryptographic Nonce for Sign in with Apple (SECURITY-12)

### Applies To
`FirebaseAuthService.signInWithApple()`

### Design
Apple requires a cryptographic nonce when using Sign in with Apple with Firebase. This prevents replay attacks — an attacker who intercepts the Apple credential cannot reuse it.

```
Flow:
1. Generate random nonce (32 bytes)
2. SHA256-hash the nonce → hashedNonce
3. Pass hashedNonce to ASAuthorizationAppleIDRequest
4. Apple signs the hashedNonce into the identity token
5. Pass rawNonce + Apple identity token to Firebase
6. Firebase verifies: SHA256(rawNonce) == hashedNonce in token ✓
```

The nonce is generated by `AppleSignInNonceGenerator` (see logical-components.md). This is a standard requirement — not optional.

## Pattern 3: Firebase Error Mapping (SECURITY-15)

### Applies To
`FirestoreService`, `FirebaseAuthService` — all async throws methods

### Design
Raw Firebase errors (e.g. `FirestoreError.unavailable`, `AuthError.networkError`) are caught at the service layer and mapped to a typed `AppError` enum before being thrown to ViewModels. ViewModels only see `AppError` — never Firebase internals.

```
FirestoreService.saveProfile() throws
  ├── catch FirestoreError.unavailable → throw AppError.networkUnavailable
  ├── catch FirestoreError.permissionDenied → throw AppError.permissionDenied
  └── catch any other → throw AppError.unknown
```

ViewModel handles:
```swift
catch AppError.networkUnavailable {
    fieldError = "Save failed. Please check your connection and try again."
}
catch {
    fieldError = "Save failed. Please try again."
}
```

No raw Firebase error description ever reaches the UI.

## Pattern 4: Offline-First Data Access (Reliability)

### Applies To
`FirestoreService` (reads), `CoreDataOfflineQueue` (session writes)

### Design
Two complementary layers handle offline scenarios:

**Layer 1 — Firestore persistent cache (reads)**
Profile and zone reads are served from local disk cache when offline. `PersistentCacheSettings` is set once at app startup. No special offline code needed in the service layer — Firestore SDK handles it transparently.

**Layer 2 — Manual Core Data queue (session writes)**
Session data must be reliably queued when Firebase is unreachable. The manual queue gives full control over retry timing and sync confirmation.

```
Workout ends
  │
  ├── Firebase reachable?
  │     ├── YES → firebaseService.saveSession() → done
  │     └── NO  → offlineQueue.enqueue(session) → stored locally
  │
Network reconnects (NWPathMonitor fires)
  └── firebaseService.syncPendingSessions()
        ├── offlineQueue.pendingSessions()
        └── for each: upload → markSynced → remove from queue
```

The two layers handle different data types and different failure modes — they work together, not as alternatives.

## Pattern 5: Network Monitoring (Reliability)

### Applies To
`NetworkMonitor` (singleton in `AppContainer`)

### Design
`NWPathMonitor` runs on a background queue and publishes connectivity status changes via an `AsyncStream<Bool>`. `FirestoreService` observes this stream and triggers `syncPendingSessions()` whenever the path transitions from unsatisfied → satisfied.

```swift
// NetworkMonitor publishes changes
networkMonitor.isConnectedStream  // AsyncStream<Bool>

// FirestoreService observes
for await isConnected in networkMonitor.isConnectedStream {
    if isConnected { await syncPendingSessions() }
}
```

One `NWPathMonitor` instance shared across the app — created in `AppContainer`, never duplicated.

## Pattern 6: HealthKit Authorization State Monitoring (Usability)

### Applies To
`HealthKitService`, `HomeViewModel`

### Design
HealthKit authorization status is checked:
1. On app foreground (via `scenePhase` change to `.active`)
2. After the user grants access in Settings and returns to the app

`HomeViewModel` observes `scenePhase` and re-checks `healthKitService.isAuthorized` on every foreground activation. If status has changed from denied to authorized, the Start Workout button re-enables without requiring an app restart.

```
App comes to foreground
  └── HomeViewModel detects scenePhase == .active
        └── healthKitService.isAuthorized?
              ├── true  → startWorkoutEnabled = true
              └── false → startWorkoutEnabled = false
                          show instruction + "Open Settings" link
```

## Pattern Summary

| Pattern | Category | Components |
|---|---|---|
| Repository via protocols | Maintainability | All 4 service protocols |
| Cryptographic nonce | Security (SECURITY-12) | `AppleSignInNonceGenerator`, `FirebaseAuthService` |
| Firebase error mapping | Security (SECURITY-15) | `AppError`, all service `catch` blocks |
| Offline-first (dual layer) | Reliability | `FirestoreService` cache + `CoreDataOfflineQueue` |
| Network monitoring | Reliability | `NetworkMonitor`, `FirestoreService` |
| HealthKit state monitoring | Usability | `HealthKitService`, `HomeViewModel` |
